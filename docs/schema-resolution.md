# Разрешение схем

Во время выполнения система разрешения объединяет кандидаты Schema.org вдоль активного контекста страницы: от
наименее конкретного ресурса к наиболее конкретному. Интеграционные плагины определяют собственные имена
контекстов, поэтому ядру не требуется знать обо всех типах сущностей компонентов.

## Путь контекста

Узел контекста состоит из имени контекста и идентификатора сущности. Вместе они образуют его уникальный ключ:

```php
$category = new ContextNode('com_shop.category', 15);
$product  = new ContextNode('com_shop.product', 73);
$variant  = new ContextNode('com_shop.variant', 81);

$path = (new ContextPath())
    ->append($category)
    ->append($product)
    ->append($variant);
```

Добавленные позднее узлы являются более конкретными и переопределяют значения, предоставленные предыдущими
узлами.

## Переопределения пунктов меню

Переопределение пункта меню вставляется сразу после области ресурса, для которой оно настроено. Поэтому оно
становится наиболее конкретным кандидатом для этой области:

```php
$path->insertAfter($article->getKey(), new ContextNode('com_menus.item', 100));
```

Область не обязана совпадать с целью маршрута пункта меню. Например, у пункта меню категории есть отдельные
настройки для страницы категории и для материалов, открытых при активном `Itemid`. Настройка материала
добавляется после текущего материала и поэтому переопределяет настройки материала, категории и глобальные
настройки.

Пустая настройка меню означает наследование и не добавляет кандидата меню. Явное значение «Отключить»
останавливает соответствующую цепочку наследования и не создаёт основную схему для этой области.

У пунктов меню коллекций есть отдельный параметр `page_schema_type` для самой страницы меню. Он не наследуется:
пустое значение означает, что страница не создаёт основную схему. Страницы избранных материалов и архива также
могут предоставлять шаблон `item_*` для материала или контакта, открытого с этим `Itemid`. Страница списка всех
категорий вместо этого предоставляет только шаблон `category_*`. Это ограничивает путь переопределения двумя
уровнями и не позволяет пункту меню категорий неявно переопределять материал или контакт внутри выбранной
категории.

## Кандидаты и UID

Кандидат регистрируется для одного узла контекста:

```php
$registry->add(
    $variant,
    new SchemaCandidate('primary', $schemaData, priority: 10),
);
```

Кандидаты с одинаковым `uid` описывают одну логическую схему и объединяются. Кандидаты с разными UID остаются
отдельными выходными схемами. Более высокий `priority` имеет преимущество только среди кандидатов одного узла
контекста; при сравнении разных узлов приоритет всегда определяется конкретностью пути.

Значения объединяются по свойствам верхнего уровня. `null` означает, что кандидат не предоставляет значение,
и не удаляет унаследованное значение. Ноль, `false` и пустая строка являются допустимыми значениями и
сохраняются.

## Обязанности интеграции

Интеграционный плагин должен:

1. Распознать текущую страницу компонента.
2. Построить путь контекста от наименее конкретной сущности к текущей.
3. Вставить явное переопределение активного пункта меню после области сущности, для которой оно настроено.
4. Загрузить и зарегистрировать кандидатов схем для применимых узлов.

Например, магазин может построить такой путь без изменения основной системы разрешения:

```text
com_shop.category:10
com_menus.item:100
com_shop.category:15
com_shop.product:73
com_shop.variant:81
```

Здесь пункт меню настраивает категорию `10`. Вариант является наиболее конкретным контекстом и поэтому имеет
преимущество при конфликтах с кандидатом меню для категории, другими категориями и родительским товаром. Если пункт меню вместо
этого предоставляет настройку для варианта, интеграция вставляет её после варианта.

## Сбор и формирование разметки

Системный плагин собирает схемы во время события Joomla `onAfterRender`. Сбор выполняется только для клиентской
части сайта с HTML-документом и пропускается для запросов `com_ajax`. Плагины группы `microschema` загружаются
до отправки события `onMicroschemaCollectSchemas`.

Интеграционный плагин может подписаться на событие сбора:

```php
use Joomla\Component\Microschema\Administrator\Event\CollectSchemasEvent;

public static function getSubscribedEvents(): array
{
    return [
        CollectSchemasEvent::NAME => 'collectSchemas',
    ];
}

public function collectSchemas(CollectSchemasEvent $event): void
{
    $category = $event->appendContext('com_shop.category', 10);
    $variant  = $event->appendContext('com_shop.variant', 81);

    $event->addMenuOverride($category->getKey(), 100);
    $event->addSchema($variant->getKey(), 'primary', [
        '@type' => 'Product',
        'name'  => 'Вариант товара',
    ]);
}
```

После завершения всех подписчиков система разрешения объединяет кандидатов. Каждый разрешённый UID выводится
отдельным тегом `<script type="application/ld+json">`. Если контекст Schema.org отсутствует, средство вывода
добавляет его, а также кодирует ограничители HTML-тегов, чтобы значения схемы не могли преждевременно закрыть
тег `script`.

Перед выводом системный плагин добавляет стабильные идентификаторы известным сущностям Schema.org, если явный
`@id` отсутствует. Общесайтовые объекты `Organization` и `WebSite` используют корень сайта; `WebPage`,
`CollectionPage`, `BreadcrumbList`, материалы и списки используют URL текущей страницы или сущности. Если на
странице есть несколько объектов `ItemList`, в их фрагмент включаются стабильный UID кандидата и путь вложенного
свойства. Явные идентификаторы всегда сохраняются.

Когда включена настройка компонента для навигационной цепочки (`BreadcrumbList`) и соответствующий объект
действительно создан, каждый объект `WebPage` или `CollectionPage` без явного свойства `breadcrumb` получает
ссылку `@id` на этот список. При
отключённых навигационных цепочках, отсутствии списка или наличии явной ссылки страницы ничего не меняется.

Свойства, объявленные в Schema.org как `Date` или `DateTime`, нормализуются рекурсивно, включая вложенные
материалы в `ItemList`. Для дат используется формат `YYYY-MM-DD`. Значения даты и времени без явного смещения
считаются значениями базы данных Joomla в UTC, преобразуются в настроенный часовой пояс сайта и выводятся в
формате ISO 8601. Некорректные и нулевые даты Joomla исключаются.

Все теги объединяются в один блок, ограниченный комментариями `<!-- MicroSchema: start -->` и
`<!-- MicroSchema: end -->`. Настройка компонента `output_position` определяет, будет ли этот блок вставлен
непосредственно перед `</head>` или `</body>` в сформированном ответе. Если реестр разрешается в пустую
коллекцию или выбранный закрывающий тег отсутствует, блок не добавляется.

Когда включены настройки компонента `schemaorg_enabled` и `schemaorg_check_existing_markup`, системный плагин
перед выводом собственных тегов проверяет страницу на наличие JSON-LD и микроразметки Schema.org. Созданная
корневая схема пропускается, если на странице уже существует тот же `@type`; существующая разметка никогда не
изменяется. При включённом режиме отладки Joomla каждая пропущенная схема записывается в журнал отладки в
категории `com_microschema`.

Отключение `schemaorg_enabled` предотвращает вывод всей создаваемой JSON-LD-разметки Schema.org. Настройки
`socials_enabled` и `socials_check_existing_markup` зарезервированы для средства вывода социальных метаданных.
`ExistingSocialMetadataChecker` может фильтровать создаваемые теги `<meta>` по атрибуту `property` или `name`,
не изменяя существующую разметку страницы. При включённом режиме отладки Joomla имя каждого пропущенного
метатега записывается в журнал отладки в категории `com_microschema`.

Включённые глобальные настройки компонента `Organization` и `WebSite` регистрируются как корневые кандидаты,
если их формы содержат хотя бы одно значение. `BreadcrumbList` создаётся из навигационного пути Joomla, когда
включён параметр `breadcrumblist_enabled`. Эти кандидаты используют UID `global.organization`,
`global.website` и `global.breadcrumb` и проходят через те же средства разрешения и проверки дубликатов, что и
схемы, предоставленные интеграциями.

Кандидаты социальных метаданных используют тот же путь контекста и те же правила разрешения, что и кандидаты
Schema.org, но хранятся в отдельном реестре. Интеграции добавляют их методом `addSocialMetadata()`, используя
зарегистрированное имя социального дескриптора как `@type`. Включённые кандидаты выводятся в виде тегов `<meta>`,
при необходимости фильтруются с учётом существующих метаданных страницы и вставляются перед `</head>` внутри
блока с маркерами `MicroSchema Social`.

## Добавление схем из произвольного PHP-кода

Компоненту `com_microschema` принадлежит один `SchemaCollector` на запрос. Модули, шаблоны компонентов, макеты,
вспомогательные классы и другой PHP-код могут получить этот сборщик из загруженного компонента:

```php
use Joomla\CMS\Factory;
use Joomla\Component\Microschema\Administrator\Extension\MicroschemaComponent;

$component = Factory::getApplication()->bootComponent('com_microschema');

if ($component instanceof MicroschemaComponent) {
    $component->getSchemaCollector()->addSchema(
        uid: 'module.' . $module->id,
        data: [
            '@type' => 'Organization',
            'name'  => 'Схема модуля',
        ],
    );
}
```

Если `contextKey` не указан, кандидат привязывается к `microschema.page:root` — наименее конкретному контексту
активного пути. Это подходит для схем с собственным UID и резервных значений. Код, которому требуется
переопределить конкретный материал, товар или вариант, может явно передать соответствующий контекст:

```php
$collector->addSchema(
    uid: 'primary',
    data: $schemaData,
    contextKey: 'com_shop.variant:81',
);
```

Кандидат можно зарегистрировать до того, как интеграционный плагин добавит его узел контекста. Он будет
участвовать в разрешении, как только этот узел появится в активном пути. Все добавления должны произойти до
завершения системным плагином события `onAfterRender`; более поздние добавления не могут повлиять на ответ.

## Модуль MicroSchema

Модуль `mod_microschema` регистрирует настроенные данные Schema.org в общем сборщике во время его вывода
системой Joomla. Кандидат привязывается к корневому контексту страницы и использует
`module.microschema.<module-id>` как UID, поэтому несколько экземпляров модуля остаются независимыми.

Модуль преобразует `schema_type` в `@type` и нормализует значения из `schema_properties`, включая вложенные
объекты Schema.org и повторяемые свойства. Он не создаёт видимого HTML. Модуль должен быть опубликован, назначен
текущему пункту меню и выведен в позиции активного шаблона; назначенный, но не выведенный модуль не может
зарегистрировать свою схему.
